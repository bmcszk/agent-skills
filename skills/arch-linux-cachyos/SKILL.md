## Hard constraints (from user feedback)

1. **AI agent must not invoke `sudo` directly.** Scripts that need root use `sudo` internally.
2. **All fix scripts must be idempotent** (safe to re-run).
3. **User wants 300% certainty on kernel/bootloader changes.** Investigate online; check the actual binary; verify the fix ran.
4. **Avoid kernel panic risk.** Kernel cmdline and initramfs changes are the highest-risk surface.

## Pacman / `pacman.conf`

### IgnorePkg placement (the #1 recurring bug)

**`IgnorePkg` MUST be in the `[options]` section.** Anywhere else (end of file, `[multilib]`, etc.) → pacman prints `directive 'IgnorePkg' in section '<name>' not recognized` and **silently ignores it**.

- Source: `pacman.conf(5)` — https://man.archlinux.org/man/pacman.conf.5.en
- Separator: **space**, not comma
- Validation: `pacman-conf IgnorePkg` (same parser pacman uses)
- The CachyOS default `pacman.conf` has a commented `#IgnorePkg   =` in `[options]` — uncomment and populate that line

### Removing the running kernel is safe

Per ArchWiki/Reddit: "It is safe to remove either [kernel] as long as you have another kernel installed that you can boot into." The running kernel stays in memory; only disk files are removed.

### IgnorePkg does not block removal

Per `pacman.conf(5)`: IgnorePkg only affects `--sysupgrade` (upgrades), **not** `--remove`. So `pacman -Rns` works even on IgnorePkg'd packages.

## Kernel switching (the SIMPLE way)

**To switch default kernel: just remove the one you don't want.**

```bash
# Verify the kernel you want to keep has boot files:
sudo ls /boot/vmlinuz-linux-cachyos-lts /boot/initramfs-linux-cachyos-lts.img

# Remove the other kernel — pacman hooks auto-regenerate /boot/limine.conf
sudo pacman -Rns linux-cachyos linux-cachyos-headers

# Reboot into the remaining kernel
sudo reboot
```

**Why this works:**
1. Pacman hooks (`60-limine-mkinitcpio-remove-pre.hook` + `90-limine-mkinitcpio-remove-post.hook`) fire on kernel package removal and call `limine-mkinitcpio-remove` which regenerates `/boot/limine.conf` with only the remaining kernel
2. The `limine-entry-tool` template hardcodes `default_entry: 2` — after removing the non-LTS kernel, the limine.conf structure is `/+CachyOS` (entry 1 = directory) → `//linux-cachyos-lts` (entry 2 = the only kernel). So `default_entry: 2` naturally points to LTS
3. No need to edit `/etc/default/limine`, `/boot/limine.conf`, or write hooks

**Do NOT overcomplicate this with:** BOOT_ORDER changes, `default_entry` hooks, custom post-install scripts, `/etc/boot/hooks/post.d/` entries. All of those were tried and failed. The pacman hooks are designed for exactly this use case.

### Installing a new kernel

Use the CachyOS Kernel Manager GUI (`cachyos-kernel-manager`) or:
```bash
sudo pacman -S linux-cachyos-lts linux-cachyos-lts-headers
sudo mkinitcpio -P    # regenerate all initramfs
```

## Limine bootloader

### Architecture

```
/etc/default/limine           → user-editable source (KERNEL_CMDLINE, BOOT_ORDER, ESP_PATH)
                                          │
                              sudo limine-update
                                          │
                                          ▼
/boot/limine.conf (vfat)      → regenerated from /etc/default/limine + limine-entry-tool template
                                          │
                              /etc/boot/hooks/post.d/*  (run after regeneration)
```

### Key facts

| Fact | Source |
|---|---|
| `/etc/default/limine` is the user-editable source | CachyOS wiki: `wiki.cachyos.org/configuration/boot_manager_configuration/` |
| `/boot/limine.conf` is regenerated by `sudo limine-update` | Local `limine-update` binary |
| `limine-entry-tool` template hardcodes `default_entry: 2` | `strings /usr/lib/limine/limine-entry-tool` |
| `default_entry` accepts numeric (`1`) or path (`CachyOS/linux-cachyos-lts`) | Limine CONFIG.md: `codeberg.org/Limine/Limine/raw/branch/trunk/CONFIG.md` |
| `/etc/boot/hooks/post.d/` scripts run after limine regen | `limine-common-functions` → `run_boot_hooks post` |
| Hooks must be executable and not end in `.disabled` | `run_boot_hooks()` in `limine-common-functions` |

### `default_entry: 2` explained

The CachyOS limine.conf structure is:
```
/+CachyOS              # Entry 1 (OS directory)
//linux-cachyos        # Entry 2 (kernel under the OS dir)
//linux-cachyos-lts    # Entry 3 (another kernel, if installed)
```

`default_entry: 2` always points to the FIRST kernel entry (under the OS directory). If you remove the non-LTS kernel, entry 2 becomes `linux-cachyos-lts`. So `default_entry: 2` naturally works.

### `BOOT_ORDER` in `/etc/default/limine`

Controls the ORDER of kernel entries written to `/boot/limine.conf`. Glob patterns: `*lts`, `*fallback`, `*`, `Snapshots`. Does NOT control which entry is the default — that's `default_entry` in `/boot/limine.conf`.

### `/boot` is vfat with restrictive permissions

`/boot` is mounted with `fmask=0077,dmask=0077` — only root can read/write. All scripts that touch `/boot/limine.conf` need `sudo`.

## mkinitcpio

### EDID firmware injection pattern

To make a connector always report "connected" (for headless/Sunshine use):

1. Extract EDID from a real monitor: `/sys/class/drm/card1-HDMI-A-1/edid` → `/lib/firmware/edid/monitor.bin`
2. Add to mkinitcpio: `FILES=(/lib/firmware/edid/monitor.bin)` in `/etc/mkinitcpio.conf`
3. Add kernel params: `drm.edid_firmware=HDMI-A-1:edid/monitor.bin video=HDMI-A-1:e`
4. `sudo mkinitcpio -P && sudo limine-update`
5. Verify: `lsinitcpio /boot/initramfs-linux-cachyos-lts.img | grep edid`

### `amdgpu` in `MODULES=()`

Early-loads amdgpu in initramfs so KMS + EDID injection work at mode-set time, before userspace starts.

## CachyOS kernels

| Kernel | Base | Stability | Use case |
|---|---|---|---|
| `linux-cachyos` | latest stable (7.0.x) | Bleeding edge | Default if unsure; has AutoFDO |
| `linux-cachyos-lts` | longterm (6.18.x) | "Minimally patched for maximum stability" | Stable fallback; fewer regressions |
| `linux-cachyos-deckify` | latest stable | Handheld-specific patches | CachyOS Handheld ISO default |

Source: `wiki.cachyos.org/features/kernel`

### LTS vs main: what you lose

- **AutoFDO + Propeller** (main only): 1-5% on kernel-heavy benchmarks; negligible for GPU-bound gaming
- **Newest BORE patches** (main only): marginal scheduler tuning
- **Color Pipeline API for HW HDR** (6.19+): only if using HDR over HDMI
- **New amdgpu features**: sometimes new features, sometimes new regressions

What you keep on LTS: BORE scheduler, CachyOS base patchset, full 890M/Zen 5/NPU support (all in tree since 6.8/6.6).

## Display / compositor issues

### KWin doesn't re-enable display after gamescope teardown

On kernel 7.0.12, KWin may leave `HDMI-A-1` in `enabled: disabled, dpms: Off` after gamescope exits. Symptoms: black screen after "Switch to Desktop" in Steam Big Picture.

**Workaround:** `qdbus6 org.kde.KWin /KWin org.kde.KWin.replace` (restarts KWin, re-detects outputs)

**Fix:** switch to `linux-cachyos-lts` (older amdgpu display-handoff code is more stable)

### Steam "Switch to Desktop" in Big Picture

Steam's legacy path calls `steamos-session-select plasma` which:
1. Sets autologin to `plasma.desktop` via `pkexec`
2. Shuts down Steam
3. Stops `gamescope-session.target`

The `cachyos-gamescope-autologin.service` then reverts autologin to `gamescope-session.desktop` on every desktop login. Use `steamos-session-select persistent` to mask this behavior.

### Sunshine autostart

Sunshine's systemd user service (`app-dev.lizardbyte.app.Sunshine.service`) must be **enabled** to autostart:
```bash
systemctl --user enable app-dev.lizardbyte.app.Sunshine.service
```

The service has `ExecStartPre=/bin/sleep 5` to avoid racing with KWin.

## signal-cli / Java (Hermes Signal gateway)

**signal-cli is a JVM app.** If Java is missing, the daemon cannot start and loops in
`activating (auto-restart)` — Hermes gateway then shows
`cannot reach signal-cli at http://127.0.0.1:41511`.

### Diagnosis

```bash
systemctl --user status signal-cli-daemon
journalctl --user -u signal-cli-daemon --no-pager -n 20
# look for: ERROR: JAVA_HOME is not set and no 'java' command could be found in your PATH
```

### Fix

```bash
sudo pacman -S jre-openjdk-headless
sudo archlinux-java status                     # discover installed JVM path
# → typically /usr/lib/jvm/java-21-openjdk

# Patch the user service to set JAVA_HOME
sed -i '/Environment=SIGNAL_CLI_DATA_DIR=/i Environment=JAVA_HOME=/usr/lib/jvm/java-21-openjdk' \
    ~/.config/systemd/user/signal-cli-daemon.service

systemctl --user daemon-reload
systemctl --user restart signal-cli-daemon
systemctl --user status signal-cli-daemon
```

Hermes gateway reconnects automatically every ~300s on retry. To force it now,
restart the gateway container.
